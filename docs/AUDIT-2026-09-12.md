## High severity

### 1 — SSRF: IPv4-mapped IPv6 loopback bypasses the private-host guard

**Severity: High**

**Location**

- `server/services/brightdata.ts:1104-1130` — `PRIVATE_IP_PATTERNS`, `isPrivateOrInternalHost()`
- `server/services/brightdata.ts:1132-1155` — `nativeHttpScrape()` (performs the real `fetch`)
- Reachable from `scrapeAsMarkdown()` at `server/services/brightdata.ts:1253` and `:1305`

**What happens**

`isPrivateOrInternalHost()` matches the raw hostname string against regexes. Node's WHATWG `URL`
normalises IPv4-mapped IPv6 addresses into a bracketed hex form:

```
new URL('http://[::ffff:127.0.0.1]:34567/').hostname  ->  '[::ffff:7f00:1]'
```

`'[::ffff:7f00:1]'` matches none of the patterns (`^::1$` requires exactly `::1`; `^127\.` cannot
match because the string starts with `[`). Unlike `siteProbe.normalizeDomainUrl`, `nativeHttpScrape`
has **no "must contain a dot" requirement**, so the request proceeds and Node connects to
`127.0.0.1`.

**Reproduction**

```ts
// local loopback-only service on 127.0.0.1:34567, then:
await scrapeAsMarkdown('http://[::ffff:127.0.0.1]:34567/', 5000);
```

Observed:

```
--- direct fetch via IPv4-mapped IPv6 loopback ---
status 200 | body contains INTERNAL: true

--- scrapeAsMarkdown() with the mapped-loopback URL ---
result: "INTERNAL SECRET SERVICE This content was fetched from a loopback-only service. ..."
```

The guard did not block it and the loopback service body was returned.

**Other unblocked ranges** (measured against the same pattern list):

| Host                 | Blocked? | Note                                                                  |
| -------------------- | -------- | --------------------------------------------------------------------- |
| `[::ffff:127.0.0.1]` | **no**   | IPv4-mapped loopback — the exploit                                     |
| `fd00::1`, `fd12::1` | **no**   | `/^fc00:/` only matches the literal `fc00:` prefix; ULA is `fc00::/7`  |
| `fe90::1`, `fea0::1` | **no**   | `/^fe80:/` only matches `fe80:`; link-local is `fe80::/10`             |
| `100.64.0.1`         | **no**   | CGNAT `100.64.0.0/10` not covered                                     |
| `198.18.0.1`         | **no**   | benchmarking range not covered                                        |
| `[fd00::1]`          | **no**   | bracketed form bypasses every pattern                                 |
| `169.254.169.254`    | yes      | covered                                                               |
| `10.0.0.1`           | yes      | covered                                                               |
| `0.0.0.0`            | yes      | covered                                                               |

**Why it matters**

Scrape targets are derived from discovered evidence (`siteProbe.deriveCompanyDomainWithProvenance`
extracts URLs out of search-result snippets), i.e. from content the app does not control. A page that
appears in a discovery run can steer the local process into fetching internal addresses — including
Apex's own API on `127.0.0.1:3000`.

**Suggested fix**

1. Strip brackets and normalise IPv4-mapped IPv6 to dotted-quad before matching:
   `[::ffff:7f00:1]` → `127.0.0.1`, then re-check.
2. Replace the regex list with numeric range checks (`net.isIP` + CIDR comparison) covering
   `10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`, `100.64/10`, `198.18/15`, `0/8`,
   `::1/128`, `fc00::/7`, `fe80::/10`, `::ffff:0:0/96`.
3. Note that a string check cannot catch DNS rebinding (`evil.com` → `127.0.0.1`). For full
   coverage, resolve the hostname and validate the resulting IP(s), or re-validate after resolution
   immediately before connecting.

## Medium severity

### 2 — Concurrent lead conflicts deadlock the per-lead patch queue

**Severity: Medium-High**

**Location**

- `src/context/LeadContext.tsx:284-306` — `conflictModal` state, `openConflictDialog()`
- `src/context/LeadContext.tsx:486-490` — the promise that awaits the user's choice
- `src/context/LeadContext.tsx:467-547` — `reconcileLeadPatch()` per-lead queue

**What happens**

`conflictModal` holds exactly **one** `onResolve` callback, and `openConflictDialog()` overwrites it
unconditionally:

```ts
const openConflictDialog = useCallback((localLead, serverLead, onResolve) => {
  setConflictModal({ open: true, localLead, serverLead, onResolve });   // overwrites
}, []);
```

When a patch hits HTTP 409, `reconcileLeadPatch` parks on a promise that only the dialog can settle:

```ts
const resolvedLead = await new Promise<Lead | null>((resolve) => {
  openConflictDialog(lead, error.currentLead, (userChoice) => resolve(userChoice));
});
```

The queue is keyed **per lead**, so conflicts on two *different* leads are not serialised against
each other. If lead A and lead B both return 409 before the user answers, B's `onResolve` replaces
A's. The user's answer settles B only — **A's promise never settles**:

- A's `operation` never resolves, so the `.finally` at line 541 never runs.
- `leadPatchQueuesRef` keeps A's entry forever (a leak).
- Every later patch for A chains on that never-settling promise
  (`previousOperation = existingOperation`), so **all future edits to lead A silently never
  persist**. The UI shows the optimistic value and no error.

**Reproduction**

A minimal script mirroring the queue + single-slot resolver:

```
Scenario: lead A and lead B both hit HTTP 409 before the user answers.

  [lead-A] 409 -> opening conflict dialog
  [lead-B] 409 -> opening conflict dialog

  queue size before user answers: 2
  user answers the (single) visible dialog for lead-B

  [lead-B] dialog resolved -> { id: 'lead-B', resolved: true }
  opA: STILL PENDING
  queue entries still held: [ 'lead-A' ]

  Now try a further edit on lead-A:
  opA2: STILL PENDING   <-- lead-A is permanently blocked
```

**Reachability**

`reconcileLeadPatch` is invoked from six handlers (`:609`, `:810`, `:833`, `:852`, `:883`, `:957`).
Two of them are on the hot path for concurrency:

- `:883` (`handleUpdateLeadsFields`) is **fire-and-forget** — `void reconcileLeadPatch(...)` — so it
  is in flight while the user can immediately act on another lead.
- Any edit on lead A while lead B's patch is still awaiting its 409 resolution.

Two independent 409s landing before the user clicks is therefore entirely reachable — e.g. a
discovery run finishing (which rewrites leads) while the user edits a different lead.

**Suggested fix**

Queue the conflicts rather than overwriting the slot. Either:

1. Keep an array of pending conflicts and render them one at a time, or
2. When a new conflict arrives while one is open, auto-resolve the previous one (e.g. resolve with
   `null` = "accept server version") and log it.

Option 2 is a small change and guarantees the queue always drains:

```ts
const openConflictDialog = useCallback((localLead, serverLead, onResolve) => {
  setConflictModal(prev => {
    if (prev.open && prev.onResolve) prev.onResolve(null as any); // settle the orphan
    return { open: true, localLead, serverLead, onResolve };
  });
}, []);
```

### 3 — `GET /leads?limit=abc` silently returns a single lead

**Severity: Medium**

**Location:** `server/routes/api.ts:265-268`

```ts
const parsedLimit =
  limit !== undefined
    ? Math.min(Math.max(Number(limit) || 1, 1), 5000)
    : undefined;
```

`Number('abc')` is `NaN`; `NaN || 1` evaluates to `1`, so the clamp "succeeds" with a value of 1
instead of falling back to the default page size.

Measured outcomes:

```
limit=undefined  GET /leads -> undefined   (fast path: returns ALL leads)
limit=abc        GET /leads -> 1           <-- silently truncated
limit=           GET /leads -> 1           <-- silently truncated
limit=50         GET /leads -> 50
```

So `GET /leads` (no params) returns the full inventory, while `GET /leads?limit=` returns exactly
one row. A client that sends an empty or malformed `limit` sees a near-empty list and no error.

**Suggested fix:** parse once with an explicit fallback, e.g.

```ts
const n = Number(limit);
const parsedLimit = Number.isFinite(n) && n > 0 ? Math.min(Math.floor(n), 5000) : undefined;
```

### 4 — Non-numeric `limit` produces an HTTP 500 on two endpoints

**Severity: Medium**

**Locations:** `server/routes/api.ts:488` (`GET /leads/:id/activities`),
`server/routes/api.ts:1792` (`GET /outreach-drafts`)

Both use the form `Math.min(Math.max(Number(req.query.limit || 50), 1), 500)` — note there is no
`|| fallback` *after* `Number(...)`. `Math.max(NaN, 1)` is `NaN` and `Math.min(NaN, 500)` is `NaN`,
so `NaN` is passed to the DB layer and bound to `LIMIT ?`.

`node:sqlite` rejects NaN bindings (verified against a real in-memory database):

```
1          -> rows returned: 1
0          -> rows returned: 0
-1         -> rows returned: 5     <-- SQLite treats LIMIT -1 as "no limit"
200        -> rows returned: 5
NaN        -> ERROR: datatype mismatch
null       -> ERROR: datatype mismatch
```

The route's `try/catch` therefore returns **500 Internal Server Error** for
`GET /leads/:id/activities?limit=abc` — malformed client input surfacing as a server fault rather
than a 400 or a sane default.

**Suggested fix:** validate `limit` once at the route boundary and reject or default it before it
reaches the DB layer.

### 5 — Readers accept negative / NaN limits → unbounded query or crash

**Severity: Medium**

Three read helpers do not clamp their `limit` argument the way their siblings do. Compare with the
correct pattern already used in `readMiningSessions` (`db.ts:3311`) and `readSavedSearches`
(`db.ts:2836`): `Math.min(Math.max(Math.floor(limit) || DEFAULT, 1), MAX)`.

| Function | Location | Problem |
| --- | --- | --- |
| `readLeadsSummary` | `db.ts:1377` | `if (typeof limit === "number" && limit > 0)` — for `NaN`/negative the `LIMIT` clause is **omitted entirely**, producing an unbounded scan |
| `readOutreachDrafts` | `db.ts:3739` | `.all(Math.min(limit, 200))` — no lower bound; `LIMIT -1` returns **all rows** |
| `readLeadActivities` | `db.ts:3668` | `.all(leadId, Math.min(limit, 500))` — same as above |

Measured against a throwaway database seeded with 120 leads:

```
rows in db: 120
limit=50 (valid)             -> returned   50 leads
limit=NaN (?limit=abc)       -> returned  120 leads   <-- unbounded
limit=undefined (no param)   -> returned  120 leads   <-- unbounded
limit=-1                     -> returned  120 leads   <-- unbounded
```

Today the HTTP layer partially shields these (the `GET /leads` route converts NaN to 1), so the
reachable impact is findings 3 and 4 rather than a live unbounded scan. The hazard is that the DB
layer's contract is "NaN or negative means no limit", which is the opposite of what a caller would
assume — any future caller that passes an unvalidated value silently gets a full-table scan.

**Suggested fix:** apply the same clamp inside each function so the guarantee lives with the query,
not with each caller.

### 6 — `getSnapshot` mutates the store during render

**Severity: Medium**

**Location:** `src/lib/traceStore.ts:45-58`, consumed at `src/lib/traceStore.ts:212-223`

```ts
getState(sessionId: string): MiningSessionLiveState {
  let state = this.sessions.get(sessionId);
  if (!state) {
    this.trimSessions();                       // <-- deletes other sessions
    state = { sessionId, logs: [], traceEvents: [], status: 'idle' };
    this.sessions.set(sessionId, state);       // <-- inserts
  }
  return state;
}
```

and the hook passes it straight to React as the snapshot getter:

```ts
const getSnapshot = () => {
  if (!sessionId) return DEFAULT_MINING_STATE;
  return miningTraceStore.getState(sessionId);   // mutating call
};
return useSyncExternalStore(miningTraceStore.subscribe, getSnapshot, getSnapshot);
```

`useSyncExternalStore` requires `getSnapshot` to be **pure** — React may call it during render,
multiple times, and may discard a render. Here a read has two side effects: it inserts a new entry
into `sessions` and may evict up to `trimSessions()`'s victims — all without calling `notify()`, so
subscribers are never told the map changed.

Practical consequence: merely *rendering* `TraceTerminal` for a session that isn't in the map
creates store state, and `trimSessions` can drop other sessions' cached logs/trace history as a
render-time side effect. It also breaks React's expectation that the same snapshot is returned for
the same store state, which is exactly the class of thing that produces tearing warnings.

**Suggested fix:** split the read from the write. Have `getSnapshot` return a stable frozen default
when the session is absent, and create/trim entries in `connect()` (or an explicit `ensure()` called
from an effect) instead:

```ts
getSnapshotFor(sessionId: string): MiningSessionLiveState {
  return this.sessions.get(sessionId) ?? DEFAULT_MINING_STATE;   // pure
}
```

### 8 — `ProviderTrafficController` is dead code; the rate regulator is not in the request path

**Severity: Medium**

`ProviderTrafficController` is defined at `server/services/keyRotator.ts:385-433` and exported, but
its only consumer is `test/resilienceAndCacheHygiene.test.ts`. Nothing in `server/` calls
`canAcquire()` or `recordUsage()`, and the `proactiveTokenRegulator` flag that is supposed to gate it
(documented as "Optimization 7: Proactive Token Regulator & Load Shedder … Meters sliding-window
token rates to prevent 429 rate limits") has zero read sites.

So the advertised token-rate load shedder is not active. Additionally, its API is check-then-act:
`canAcquire()` and `recordUsage()` are separate calls with no reservation, so concurrent callers can
all observe a pass before any records usage. With the engine's parallel lanes
(`Promise.all([executeTavilyLane(), executeBrightDataLane()])`) that would over-admit even once
wired up.

**Suggested fix:** either wire it into the LLM call path with an atomic `acquire()` that reserves and
returns a release handle, or remove the class and the flag.

## Low severity

### 10 — O(n²) trace de-duplication and unbounded client-side arrays

**Severity: Low-Medium** (performance)

**Location:** `src/lib/traceStore.ts:105-127`

```ts
} else if (Array.isArray(data.traceEvents) && data.traceEvents.length > 0) {
  const seenIds = new Set(state.traceEvents.map(e => e.id));        // O(n) over ALL history
  const newEvents = data.traceEvents.filter(e => !seenIds.has(e.id));
  if (newEvents.length > 0) {
    nextEvents = [...state.traceEvents, ...newEvents];              // grows without bound
  }
}
```

The server deliberately streams only deltas (`sessionStreamHub` polls every 250 ms and sends just the
new slice), and it caps its own in-memory buffers. The client undoes that advantage: it rebuilds a
`Set` over the **entire accumulated history** on every frame, and the arrays are never trimmed.

Over a long session this is O(frames × events) — a 5,000-event session rebuilds a 5,000-entry Set on
every incoming frame. The same pattern applies to `logs` (`nextLogs = [...state.logs, ...data.logs]`).

**Suggested fix:** keep a persistent `Set<string>` of seen ids alongside the array (add on ingest,
clear on `resetSession`), and cap the retained arrays (e.g. keep the last N events, mirroring the
server's `LEAD_TELEMETRY_MAX_EVENTS`).

### 11 — `suppressSocketError` conditional is a no-op; every socket error is hidden

**Severity: Low**

**Location:** `server.ts:26-45`

```ts
const suppressSocketError = (err: any) => {
  if (err?.code === "ECONNRESET" || err?.code === "EPIPE" || /* ... */) {
    return;
  }
};
```

The early `return` is the only statement in the function, so the branch has no effect: the handler
behaves identically whether or not the error is one of the intended "benign disconnect" codes.
Because it is registered as the `error` listener on `req`, `res`, and `req.socket`, **all** socket
errors are silently discarded — including genuine ones that would otherwise surface.

**Suggested fix:** make the non-suppressed branch do something meaningful:

```ts
const suppressSocketError = (err: any) => {
  if (isBenignDisconnect(err)) return;
  console.warn("[Server] Socket error:", err);
};
```

### 12 — `notifyLeadsUpdated()` causes duplicate rehydrates

**Severity: Low**

**Location:** `src/context/LeadContext.tsx:1247-1259` (dispatch), `:428-441` (listeners)

`notifyLeadsUpdated()` does two things: dispatches a same-window `CustomEvent` **and** posts to a
`BroadcastChannel('apex_crm_leads_sync')`. The effect listens for **both**:

```ts
window.addEventListener('apex_crm_leads_updated', onCustomEvent);   // -> rehydrateLeads(true)
broadcastChannel.onmessage = (event) => { if (event.data?.type === 'LEADS_UPDATED') void rehydrateLeads(true); };
```

Per the BroadcastChannel spec, a message is delivered to every channel with the same name *except the
one that sent it*. `notifyLeadsUpdated` creates a throwaway channel, but the effect's channel is a
**different object in the same tab** — so it receives the message. Each call therefore produces two
full rehydrates, and callers that also rehydrate explicitly make it three, e.g.
`ScrapeWorkspace.tsx:406-407`:

```ts
await rehydrateLeads(true);
notifyLeadsUpdated();        // -> two more rehydrates
```

Redundant network + state churn rather than a correctness bug, but it is easy to halve.

**Suggested fix:** include a tab/origin id in the broadcast payload and ignore messages whose id
matches the sender, or drop the same-tab dispatch when the broadcast already covers it.

### 13 — `traceStore.connect()` has no reference counting

**Severity: Low** (latent)

**Location:** `src/lib/traceStore.ts:60-66`, `:185`

```ts
const existing = this.activeEventSources.get(sessionId);
if (existing && existing.readyState !== EventSource.CLOSED) {
  return () => this.disconnect(sessionId);      // cleanup kills the SHARED connection
}
...
return () => this.disconnect(sessionId);
```

A second caller for an already-connected session gets a cleanup that closes the single shared
`EventSource`. If two components ever stream the same session, the first one to unmount silently
kills the other's stream.

Currently only one call site exists (`ScrapeWorkspace.tsx:333`) and `TraceTerminal` uses the
read-only hook, so this is latent rather than live. It is worth fixing before a second consumer is
added — a simple subscriber count would do it.

### 14 — Fire-and-forget patch swallows persistence failures

**Severity: Low**

**Location:** `src/context/LeadContext.tsx:883`

```ts
if (updatedLead) {
  void reconcileLeadPatch(updatedLead, rollbackLead);   // not awaited, result ignored
}
```

Unlike its siblings (`:810`, `:833`, `:852`, `:957`), which `await` and throw a user-visible error
when persistence fails, `handleUpdateLeadsFields` discards the `Promise<boolean>`. A failed save
reverts the optimistic state via `restoreLeadSubset` but the caller reports success. No unhandled
rejection occurs (the function catches internally), so the failure is entirely silent.

**Suggested fix:** `await` it and surface the error like the neighbouring handlers, or explicitly
document that this path is best-effort.

### 15 — `uncaughtException` continues instead of exiting

**Severity: Low** · `server.ts:206-217`

The handler logs and returns, leaving the process running after an uncaught exception. This appears
deliberate ("Global guards to prevent client socket resets from terminating the Node process"), but
the benign-disconnect filter is already handled by the early return, so genuine uncaught exceptions
also leave the process in an undefined state. Consider `process.exit(1)` on the non-benign branch and
letting a supervisor restart.

---

### 16 — 10 MB body parsed before the host guard runs

**Severity: Low** · `server.ts:102` vs `server.ts:108`

`express.json({ limit: "10mb" })` is registered globally, ahead of the `/api` DNS-rebinding guard. A
rejected cross-origin request still costs a 10 MB buffer parse. Mounting the body parser after the
guard would avoid the work.

---

### 17 — ETag depends on an in-memory counter

**Severity: Low** · `db.ts:1454-1465`

The tag hashes `MAX(updated_at)`, `COUNT(*)`, `dbMutationCounter`, and the query string.
`dbMutationCounter` resets to 0 on process restart. It is combined with `MAX(updated_at)`, which comes
from the `updated_at` values written by callers (millisecond precision), so the practical risk is low
— but the tag is not derived purely from durable state, which makes cache behaviour harder to reason
about across restarts.

  migration-internal identifiers only.
- **Secret handling:** no `console.*` call logs an API key, token, or password. Keys are exposed to
  clients only as 8-char SHA-256 fingerprints (`fingerprintKey`, `keyRotator.ts:376-378`).
- **Transaction hygiene:** the multi-statement write paths (`POST /leads/:id/merge`, `DELETE /leads`,
  the `discovered_companies` upsert) each wrap work in `BEGIN IMMEDIATE` and roll back on the error
  path before rethrowing.

### Engine internals

I reviewed the engine paths most likely to hide arithmetic and state bugs, and **found no defects**.

| Area | Location | What was checked | Result |
| --- | --- | --- | --- |
| Score normalisation | `scoring.ts:162-181` | Empty/single-element pool, `total === 0`, `log2(0)` when `maxEntropy === 0` | Guarded (`scores.length < 2`, `total === 0`, `maxEntropy === 0` all early-return) |
| TF-IDF weight | `scoring.ts:191-199` | `totalDocs <= 0`, negative IDF when `docsWithTerm >= totalDocs` | Guarded; `Math.max(0, …)` clamps the negative case |
| BM25+ | `scoring.ts:416-455` | `avgdl === 0` division, empty doc, `df > totalDocs` producing `log` of a non-positive number | `avgDocLength \|\| 50` guards the divisor; the `df > totalDocs` case is unreachable (`totalDocs >= 1` keeps the log argument positive) and is clamped anyway |
| Kalman fusion | `scoring.ts:138-152` | NaN inputs, `processNoise + observationNoise === 0`, out-of-range output | Explicitly guarded on every input and the output |
| Sigmoid scaling | `scoring.ts:121-128` | `maxSigmoid - minSigmoid === 0` | Safe for the default parameters in use; would divide by zero only if called with `steepness = 0`, which no call site does |
| Bayesian intent | `scoring.ts:90-119` | `posterior` denominator → 0 | `prior` is fixed at 0.25 and `likelihoodFactor >= 0.5`, so the denominator is always ≥ 0.875 |
| Resume dedupe | `discoveryEngine.ts:1128-1198` | Double-counting query runs / rejection tallies when a checkpoint is re-saved at the same boundary | Handled — runs merge through a `round:query` key set, counters are *replaced* not merged, seen-candidate keys are re-seeded |

The engine is consistently defensive about numeric edge cases — much of it already handles the
NaN/zero/negative cases that findings 3–5 show missing in the API layer.

## Appendix: reproduction notes

Techniques used, so the findings can be re-verified:

- **Throwaway database.** `APEX_DB_PATH` was pointed at a `fs.mkdtempSync` directory to exercise
  `server/db.ts` against a seeded 120-lead database without touching `.apex-data/`. Note: the DB
  handle stays open, so `rmSync` of the temp directory throws `EBUSY` — leave it to the OS temp
  cleaner.
- **SQLite `LIMIT` semantics** were measured directly against `node:sqlite` rather than assumed.
  The result is counter-intuitive and worth remembering: `LIMIT -1` means *no limit*, and binding
  `NaN` throws `datatype mismatch` rather than being coerced.
- **SSRF** was proven with a real `http.createServer` bound to `127.0.0.1` and a real
  `scrapeAsMarkdown()` call, not by inspecting the regexes alone.
- **Frontend deadlock** was proven with a minimal script reproducing the queue + single-slot
  resolver, since the failure mode is timing-dependent and hard to trigger by hand.
